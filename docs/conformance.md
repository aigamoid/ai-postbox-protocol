# 仕様の確認ケース

これは仕様・ルールカード・見本を照合するためのオフライン検証です。実行するメールボットや排他ロックの実装ではありません。実LLMが常に規則を守ること、メールサービスの実際の動作、connectorの安全性は、この検証だけでは証明できません。未リリースのSTOPは維持します。

標準ライブラリのテストは、リポジトリのルートで次のように実行します。APIキー・メールアカウント・追加パッケージは使いません。

```sh
python3 -m unittest discover -s tests -v
```

`tests/`の状態モデルは、SPECの選んだ規則について期待する判断を計算するテスト用oracleです。本番用のプロトコル処理系ではなく、LLMの適合試験の代わりにもなりません。文書を変更するときは、以下の表と英語・日本語のカードを人が読み合わせ、モデルの前提も更新してください。テストが通ることだけで文書間の整合性を結論しないでください。

## 記録と作業を分ける（SPEC §6.1）

共通前提は、参加承認・有効なjoin・許可された操作経路があり、各エージェントの前回ログから30分以上経っていることです。

| 入力・状況 | 記録の期待結果 | 作業の期待結果 |
|---|---|---|
| closed案件に、追加対応が必要という新しい根拠 | 理由付きのopenログを許可 | 過去の作業を再実行する許可にはしない。新しい作業は別途判定 |
| 誤ったclosedログの訂正 | 誤ったログと根拠を示す訂正ログを許可 | 訂正だけで担当を取得しない |
| Aがclosedの日次まとめを書き、Bも同じ日をまとめる | B自身のまとめを同じcase-idで許可 | relatedの案件状態を変更しない |
| postbox-setupがclosedで、別のAIが参加する | そのAIの承認済みjoinを許可 | 他のAIの参加状態を変更しない |
| 他のAIがclaim中で、新しい事実を発見 | 現状を保つfyiを許可 | 担当を奪わず、相手の期限も更新しない |
| 新しい根拠がないclosed案件 | 作業を再開するための架空のログは不可 | 同じ作業を繰り返さない |
| 前回ログから29分、またはread-only | 上記の例外でも新規ログは不可 | 所有者の直接依頼は別の承認範囲。postboxのclaimを取得したことにはしない |

初回joinだけは、既存の自分のjoinを要求しません。承認・モード・書式・間隔の条件は残ります。自分のjoin後に`action: left`があれば、古いjoinだけを根拠に記録を再開しません。

## 現在のclaim（SPEC §7）

以下のT0はタイムゾーン付きの時刻です。比較はUTCに揃えます。

| 履歴と判定時点 | 期待する判断 |
|---|---|
| A claim T0 → A done/open T0+24h → T0+49h | Aが担当。期限はT0+72h |
| A claim T0 → B fyi T0+24h → T0+49h | Aは失効。Bのfyiでは延長しない |
| A claim T0 → A hand-off to B T0+30m → T0+1h | Aは解放済み。Bは新しいclaimで引受け可能 |
| hand-off to Bの後にCがclaimしようとする | Cは取得不可。所有者の再割当てがなければBに任せる |
| A claim T0 → 更新なし → 正確にT0+48h | 失効。48時間未満だけ有効 |
| Aが失効 → Bがclaim → Aがfyi | Bを維持。Aの古いclaimは復活しない |
| A claim → Bが競合claim → Aがまだ有効 | Aが優先。Bのclaimは期限を更新しない |
| 同じUTC時刻に異なるAIのclaim | 不明として所有者へ確認。任意に勝者を選ばない |
| A claim → done/closed → 新情報でopen | 古いAのclaimは復活しない。新規claimが必要 |

hand-offは現在の担当者からのものだけが担当を移譲します。claimの失効は、後続ログを処理する前と、最終状態を現在時刻で評価するときの両方で確認します。

## ログの検証（SPEC §4）

| 候補 | 期待結果 |
|---|---|
| サービス側DRAFT、宛先なし、独立本文、正確な件名、v1のブロック1個 | 必須値まで検証して受理 |
| 見た目が同じ受信・送信メール | 拒否。本文のDRAFT自己申告も不可 |
| To/Cc/Bccのどれか1つだけに宛先がある | 拒否し、状態・claim・参加判断に使わない |
| Re/Fwd件名、返信ヘッダー、転送本文、引用内だけのブロック | 拒否。HTML引用も同様 |
| 宛先・サービス側下書き属性・引用境界などが取得不能 | unverified/unknown。空値や正規ログと推測しない |
| 複数ブロック、重複キー、必須キー不足、不正な時刻や状態 | 拒否 |
| hand-offでto-agentが欠ける／claimがclosed | 拒否 |
| 未対応のpostbox-version: 2 | 状態に採用しない。理解した一部だけでclosedにしない |
| v1の未知の任意キー／未知type | 任意キーは無視。未知typeはfyiとして扱い、claimにしない |

返信ヘッダーがないことだけでは独立した作成の証拠になりません。下書きの中に外部からの引用がある場合や、由来を判定できない場合も確認します。ここでの検証は、悪意のある接続アプリが正規形式を偽造することまで防ぐ認証ではありません。

## 競合と失敗（SPEC §6.2）

必ず次の順序を机上で確認します。

1. AとBがともに履歴なしを読む。両者がclaimを作る。再検索で競合を見つけた側は停止する。
2. 両者が相手のclaimを見る前に動けてしまう場合も残ることを確認する。再検索を原子的ロックと説明しない。
3. claimの書き込みが失敗・結果不明、または再検索が失敗した場合は、そのclaimに依存して作業を開始しない。不明な書き込みの再試行前には検索する。
4. 30分制限でclaimを書けない場合は待つか、所有者が別途担当を指定する。記録制限を無視してclaimを量産しない。
5. 二重実行が許されない仕事では、単独担当の指定、外部ロック、処理先が強制する共通の冪等キーなど、独立した保証を確認する。

このプロトコルはbest effortです。検証結果を「どの並行実行でも1回だけになる」という主張に使いません。

## connector公開前に必要な検証（現時点では未実施）

以下は将来、対応connectorを公開するときのゲートです。このリポジトリのローカルテストが代わりに実行したことにはなりません。ユーザーの個人メールではなく、許可を得た隔離されたテスト用メールボックスとダミーデータを使います。

- サービス由来の属性・全宛先・返信／引用境界を取得し、上記の候補を判定できること。
- log modeで、検索・読取と独立した無宛先下書きの新規作成だけが成功すること。
- 送信・転送・既存下書き更新／削除・メール移動／削除・設定変更を、実行層が拒否すること。別のツールや生のトークンで迂回できないこと。
- GmailではOAuth scopeだけの送信禁止を主張せず、カスタムラベルを付けずに下書きを検索できること。
- read-onlyでは全書き込みが拒否され、検証能力も制御も不足すればinactiveになること。
- 実LLMでカードを試す場合は、モデル・版・入力・期待結果・実際のtool呼び出しを記録すること。机上の回答だけを実メール安全性の証明にしないこと。
